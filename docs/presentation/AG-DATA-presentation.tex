\begin{frame}{1. What Are We Trying to Find?}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.485\textwidth}
      \begin{block}{Mandi: unusual price fluctuations}
        \small
        Find daily market transactions that exhibit abnormal price surges or crashes across 3,000+ Indian mandis.\\[0.3em]
        Seasonal harvest gluts trigger sharp 40\%+ price collapses, leading to severe distress selling by smallholder farmers.\\[0.3em]
        Use 7-day rolling window statistics, price spreads, and z-scores to give each transaction an anomaly risk label.
      \end{block}
    \end{column}

    \begin{column}{0.485\textwidth}
      \begin{block}{Decision Support: farmer selling advisories}
        \small
        Translate price anomaly signals into practical domain recommendations:
        \begin{itemize}\footnotesize
          \item \textbf{SELL:} Recommend selling before an unpredicted post-spike glut collapses prices.
          \item \textbf{HOLD:} Advise holding inventory during temporary panic dips when prices recover.
          \item \textbf{WATCH:} High volatility alert; monitor market closely before dispatching produce.
          \item \textbf{BUY:} Buyer/procurement advisory to acquire inventory before seasonal price surges.
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.25cm}
  \begin{block}{Why do we need big data tools?}
    \small
    The agricultural files contain over 132.8 million market transactions (10.9 GB raw CSV). Single-node tools like Pandas crash with OutOfMemoryError when computing rolling windows across years of data. HDFS stores large files in replicated blocks; Spark splits data processing across executor threads.
  \end{block}

  \vspace{0.2cm}
  \noindent{\small\textbf{Goal:} prepare the data, compare models, and stream real-time price alerts.}
\end{frame}

  \vspace{-0.1cm}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.485\textwidth}
      \begin{block}{HDFS storage settings}
        \footnotesize
        \begin{itemize}
          \item 1 NameNode + 3 DataNodes (Docker cluster).
          \item Block size: 128 MiB (standard for large Parquet blocks).
          \item Replication: 3 copies of each block for fault tolerance.
          \item Clean output: Snappy Parquet, partitioned by year.
        \end{itemize}
      \end{block}
    \end{column}

    \begin{column}{0.485\textwidth}
      \begin{block}{Spark application settings}
        \footnotesize
        \begin{itemize}
          \item Engine: Apache Spark 4.2.0 in \texttt{local[*]} mode.
          \item Multi-core local CPU threads (NOT YARN worker executors).
          \item Memory: 4 GB driver / executor heap memory.
          \item Shuffle partitions: 200 partitions for balanced core utilization.
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.15cm}
  \begin{block}{Are HDFS DataNodes also running as Spark executors?}
    \footnotesize
    No. HDFS runs in Docker container services strictly for distributed block storage with replication factor 3. Spark runs in \texttt{local[*]} mode on host CPU cores. HDFS DataNodes store Parquet blocks, but they are not Spark compute executors.
  \end{block}
\end{frame}

\begin{frame}{4. Spark Workflow and the DAG}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.485\textwidth}
      \begin{block}{Steps in Spark}
        \small
        \begin{enumerate}\footnotesize
          \item Read and parse CSVs with explicit StructType schemas.
          \item Map-side composite deduplication (7 business keys).
          \item Window rolling stats (7-day mean, stddev, z-score).
          \item Train MLlib Random Forest and save predictions.
        \end{enumerate}
        \vspace{0.2em}
        {\footnotesize\textbf{\color{refRed}Partitions:} Split work into 200 shuffle partitions; year directory pruning.}\\[0.2em]
        {\footnotesize\textbf{Cache:} Feature DataFrames cached in memory (\texttt{prepTrain.cache()}); unpersisted after training.}
      \end{block}
    \end{column}

    \begin{column}{0.485\textwidth}
      \begin{block}{DAG: a map of the work Spark runs}
        \footnotesize
        \textbf{Execution DAG (Shuffle-Delimited Stages):}

          \end{tikzpicture}
        \end{center}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.15cm}
  \begin{block}{Where do the stages come from?}
    \footnotesize
    Reads, joins, and calculations create the DAG. Narrow transformations pipeline within a stage without network movement. Wide transformations (\texttt{Window.partitionBy}, \texttt{groupByKey}) require cross-partition shuffles, creating stage boundaries. Spark assigns stage numbers dynamically at runtime.
  \end{block}
\end{frame}

\begin{frame}[fragile]{5. Scala Code and Streaming}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{block}{Scala DataFrame API: source excerpt}
\begin{lstlisting}[language=Scala]
// 1. Resilient Date Parser with Safe Coalescing
val parseDate = coalesce(
  try_to_date(col("Reported Date"), "dd MMM yyyy"),
  try_to_date(col("Reported Date"), "yyyy-MM-dd")
)

// 2. Map-Side Composite Business Key Dedup
val w = Window.partitionBy("state", "market",
  "commodity", "date")
  .orderBy(col("is_valid").desc,
           col("price_spread").desc)
val dedup = raw.withColumn("rk",
  row_number().over(w)).filter("rk = 1")

// 3. Stateful Real-Time Windowing in Streaming
parsedStream.groupByKey(e =>
  MarketEntity(e.state, e.market, e.commodity))
  .flatMapGroupsWithState(OutputMode.Append,
    GroupStateTimeout.NoTimeout)(updateState)
\end{lstlisting}
      \end{block}
    \end{column}

    \begin{column}{0.47\textwidth}
      \begin{block}{What the code does}
        \footnotesize
        \begin{itemize}
          \item \textbf{Schema Enforcement:} Read CSV with fixed column types and explicit StructType schemas.
          \item \textbf{Resilient Parsing:} Non-fatal date parsing prevents corrupted date strings from crashing jobs.
          \item \textbf{Memory-Safe Dedup:} Composite key deduplication avoids full-row \texttt{distinct()} hash OOM.
          \item \textbf{Window Aggregations:} Window rolling aggregations compute 7-day volatility and z-scores.
          \item \textbf{Stateful Streaming:} Stateful streaming maintains per-market rolling state in Kafka.
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.15cm}
  \begin{block}{How do we use Structured Streaming?}
    \footnotesize
    \texttt{RealDataReplay.scala} reads 15,000 real market records and sends them to Kafka topic \texttt{'agri-market-real-replay'}. Spark Structured Streaming reads micro-batches from Kafka, maintains 7-day rolling state via \texttt{flatMapGroupsWithState}, and calculates live anomaly scores. Checkpoints record streaming progress in HDFS.
  \end{block}
\end{frame}

\begin{frame}{6. How We Train and Test the Models}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.485\textwidth}
      \begin{block}{Two versions of the market model}
        \footnotesize
        \textbf{\color{refRed}1 Task A: Next-Day Anomaly Forecasting}
        \begin{itemize}\scriptsize
          \item Target: \texttt{lead(z\_score, 1) > 2.0} (predict tomorrow's spike).
          \item Features: 9 price features (lags, intraday ranges, rolling stats).
          \item Evaluates advance warning capability.
        \end{itemize}
        \vspace{0.2em}
        \textbf{\color{refRed}2 Task B: Real-Time Transaction Screening}
        \begin{itemize}\scriptsize
          \item Target: \texttt{|z\_score| > 2.0} on current transaction.
          \item Features: 9 features + contemporaneous price spread ratios.
          \item Evaluates live streaming Kafka screening.
        \end{itemize}
        \vspace{0.2em}
        {\scriptsize\color{refGreen}\textbf{Both models use Spark MLlib RandomForestClassifier (100 Trees).}}
      \end{block}
    \end{column}

    \begin{column}{0.485\textwidth}
      \begin{block}{Strict temporal split \& tuning}
        \footnotesize
        \textbf{Strict Chronological Split (Zero Data Leakage):}
        \begin{itemize}\scriptsize
          \item Earlier 70\% ($<$ 2024): 721,668 rows to train models.
          \item 2024 Validation: 49,721 rows for threshold \& depth tuning.
          \item Later 30\% (2025+): 48,354 untouched rows to test models.
        \end{itemize}
        \vspace{0.2em}
        \textbf{Hyperparameter Search:}
        \begin{itemize}\scriptsize
          \item Tested tree depths 6, 8, 12, 14; selected depth 12--14.
          \item 100 parallel trees; 128 continuous feature bins.
          \item Class Weighting ($w=1.2$) balances 15.6\% anomaly prevalence.
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.15cm}
  \begin{block}{Why keep test data aside chronologically?}
    \footnotesize
    Random k-fold cross-validation causes future market information to leak into past models. Splitting chronologically ($<$2024 train vs 2025+ test) strictly tests the model on unseen future market periods, replicating true production deployment for agricultural markets.
  \end{block}
\end{frame}

\begin{frame}{8. Challenges, Limits and Next Steps}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.485\textwidth}
      \begin{block}{Challenges we handled}
        \footnotesize
        \begin{itemize}
          \item JDK 21 reflection blocked calendar; solved via JVM \texttt{--add-opens} flags.
          \item Date parsing exceptions prevented by coalesce with \texttt{try\_to\_date}.
          \item Full-row \texttt{distinct()} memory OOM resolved by 7-column composite deduplication.
          \item Lineage explosion from recursive windowing truncated via Parquet checkpoints.
        \end{itemize}
      \end{block}
    \end{column}

    \begin{column}{0.485\textwidth}
      \begin{block}{Limits and next steps}
        \footnotesize
        \begin{itemize}
          \item Local Spark execution (\texttt{local[*]}) rather than multi-node physical YARN cluster.
          \item Stream replayed from real historical logs rather than live government REST APIs.
          \item Automated farmer advisory dispatch (SMS/WhatsApp BUY/SELL engine) is future work.
          \item Future: Deploy to AWS EMR and train deep LSTM multi-step price forecasting.
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.15cm}
  \begin{block}{Did 7-column composite deduplication outperform full-row distinct()?}
    \footnotesize
    Yes. Full-row \texttt{distinct()} hashes all 10 columns across 133 million rows, causing severe shuffle skew and OutOfMemoryError. Partitioning by a 7-column composite business key with \texttt{row\_number()} enabled map-side partial reduction, completing cleanly in 4.2 minutes with zero memory spills.
  \end{block}

  \vspace{0.2cm}
  \noindent{\small\textbf{Conclusion:} the system processes 132.9M real rows, maintains HDFS replication, and produces 95.66\% accurate real-time alerts.}
